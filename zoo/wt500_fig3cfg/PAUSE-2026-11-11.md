## The storage constraint that shapes everything

Raw wcts output measured at ~4 B/record **gzipped** on disk (shard_0007:
716 MB / ~174.5M records) and ~20.6 B/record raw. Campaign total
5.704e12 records → **~23 TB gzipped**, versus a 1 TB quota. Decision made
with the user: **never store the full set: simulate on the generation
cluster in waves** (generate until near quota → `sim_shard.py` per finished
shard → wcts deleted after durable results → release next batch). Only the
small cachesim CSVs and step_cycles (~2 MB/shard) are kept and shipped via
git. The step_cycles total for the whole campaign is only a few GB.

## Performance model (measured, portable to any x86 cluster)

- **Never mmap the layer trace over a network FS**: page-fault reads run at
  1-2 MB/s. Parent-side sequential read + fork COW is the fix (in tree).
- **Native scratch**: the generator natives stream trace.bin/task.bin/out.bin
  through `$TMPDIR` at ~89 B/record of out.bin per sample. 32 natives
  interleaving on one local HDD collapse to ~5 MB/s each; `TMPDIR=/dev/shm`
  fixes it, and the shm usage counts against the job's memory cgroup.
- **Memory is the real sizing constraint**, Python-side:
  - cycle phase: ~24.4 B/record per resident LayerWeightTrace, ×10 per
    chunk (SAMPLE_CHUNK_SIZE=10): 23.9 GB observed per worker at
    ~98M records/sample.
  - stream phase: ~63 GiB peak RSS for ONE sample of the near-worst layer
    (gustavsnn dvs128_gesture layer_02_core_block3_0_0, sample 0, 11.5 min
    serial). The worst sample (489M records) extrapolates to 140-200 GiB -
    serial-only, and possibly needing >188 GB nodes (unresolved: job
    1132904 would have measured the exact coefficient; it was cancelled).
  - Default Slurm grants (1950M/cpu) cause silent page-cache thrash, not
    OOM kills. Request real memory.
- **Tiers that work**: mid shards (~20-60e9 records): 4 workers, 150G, shm
  scratch: proven by the fleet. Small shards (<20e9): would fit 60G/3-per-
  node. Heavy tail (>60e9, indices ~130-136): serial workers, full node,
  AND split into sample-window case files (fixed-count windows are wrong -
  size by cumulative records; per-sample counts come from s3_measure.py).
  The window split must NOT go through run_array.sbatch (it derives both
  case file and shard dir from the task id → collisions): invoke
  `harness.py run-shard` directly with explicit `--case-file` (e.g.
  cases_0130_w00.json; results tag comes from the stem) and `--shard-dir`
  (the parent shard's dir, shared, so gen's todo-resume no-ops the cycle
  phase). Run one dedicated cycle job per heavy shard first (gen CLI
  directly, `--sample-chunk-size 2`), then the windows with
  `--dependency=afterok`. Validate on ONE window before chaining.
- Login nodes: Stokes RLIMIT_NPROC=100 (`OPENBLAS_NUM_THREADS=1
  OMP_NUM_THREADS=1` on every command); Delta 1000-PID cgroup.
- Binaries rsynced from another cluster LOOK executable but fail on glibc -
  always rebuild natives locally (test by running, not by `-x`).
