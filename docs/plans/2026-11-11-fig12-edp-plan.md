## Energy model

Per case (arch, capture, layer, sample), per design:

```
E_dyn  = Σ_e count_e × e_access(e)          # from energy_table.json
E_leak = P_leak(design) × total_cycles / f
T      = total_cycles / f
EDP    = (E_dyn + E_leak) × T
```

Event mapping:
- Common to both designs (identical schedule): MAC/AC ops, LIF updates,
  psum/vmem buffer accesses: counts from step_cycles + schedule.
- Cache design (from cachesim counters): L1 cache reads (demand probes,
  noting the retry caveat), L1 fills, L2 accesses, L2 fills ≈ dram_accesses,
  dram_bytes × pJ/bit, prefetch tag probes.
- Scratchpad design (from tc.csv + schedule): NoC hop-packets (router energy
  × hops × packets), GB reads per send, L1 spad writes/reads (scheduler
  `temporal_traffic` per tensor as the access-count source), DRAM bytes.

Whole-model: mean over samples, sum over layers; power = E/T; area straight
from the archx table (cache: cache modules + MSHR; spad: sram modules).

Operating point (paper: "equal on-chip capacity and core count"): cache
config at parity with `zoo/wt500_fig3cfg/arch.yaml`: L1 32 KB, L2 2 MB -
policies from the pilot (khkw_split; L1 8-way LRU + next_access d4; L2
16-way pf_lru + distance_aware d4) unless the user picks otherwise. The
figure's "different prefetch and replacement configurations" multiply the
Stokes wave cost one config each: the user picks the variant list.

## Known modeling cautions (carry into T60-T63)

- Cycles-to-counts is valid only for pipelined compute units (II=1: busy
  cycles = ops). Memory and NoC events use the sims' own counters instead:
  cachesim accesses/hits/fills, tc.csv packets. Never derive memory access
  counts from cycle counts.
- Per-PE multiplicity: nocsim models a node as one mesh PE; the 4 PEs per
  node (64 total) appear only via mac_cycles. Compute and L1 energy scale by
  the real PE count.
- cachesim `l1_accesses` counts probes: a stalled request that retries is
  recounted. Fills are derived (L1 fills = misses + pf fills; L2 fills ≈
  dram_accesses). Dropped prefetches still probe tags (tag energy). MSHR
  lookups need a small-CAM energy term (paper methodology lists it).
- Leakage is a first-class term (7 nm): P_leak × T per design, and it is
  what makes the power panel differ from the energy panel.
- Frequency consistency: one campaign clock converts cycles to time; check
  CACTI access times and ASAP7 synthesis fmax all meet that clock.
- Delay definitions must align: both designs' T is the whole-layer makespan
  including compute (cachesim total_cycles vs nocsim total_cycles).
- psum/vmem (correction 2026-11-12, refined): the schedule JSONs'
  temporal_traffic/spatial_cost are solver score proxies, never counts;
  nocsim decodes psum/vmem free flags True for all 749 schedules, so psum/
  vmem GB/DRAM BOUNDARY transactions are zero. What tc.csv does carry,
  every step and under every mode: weight movement plus the intra-step
  k_chain (cross-PE psum reduction) and t_chain (LIF carry) links
  (combine.py:457); those are counted from tc.csv. Potential/psum STORAGE
  energy is analytic per arch (registers; gustavsnn potential REG file).
  Guard: never derive any count from result.metrics.temporal_traffic
  (prosperity_base.md §2-3).
- Validation + reuse: the same energy_table.json feeds RQ1's energy
  breakdown (fig:energy-profiling); sanity-check per-arch energy against the
  numbers published in each arch's paper.
