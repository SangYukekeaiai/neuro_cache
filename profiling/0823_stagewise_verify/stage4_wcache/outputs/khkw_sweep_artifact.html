Kernel-Indexed Cache Sweep

A new weight layout puts the kernel position at the bottom of the L1 set index. Forty-eight cache configurations on four layers, then the winning one on all 31 layers of both networks, five samples each, measured against nocsim.

1,115 engine-runs khkw_split layout 31 layers · vgg16 + resnet19 commit ba468ed 2026-08-31
The answer

What the sweep found

The layout works. L1 hit rates run from 87.8% to 99.7% across all 960 runs, against 76.9–91.8% for block_pack at the same point, and the best configuration lands between 1.10× and 1.82× the cycles a perfect memory system would take.

It does not beat stage 3. Against the NoC baseline the best configuration comes in at 0.71× to 1.07×, ahead on 1 layer of four. An earlier version of this page reported speedups up to 5.8×; those came from a defect in nocsim that re-sent the weight tile on every DRAM step, inflating the baseline by 2× on the vgg16 layers and 8× on R16. The defect is fixed and stage 3 re-run.

The L2 is dead on every layer. Extending the winning configuration to all 31 layers of both networks puts the L2 hit rate at 0.00% on 31 of 31. What the four-layer probe found is a property of the workload, not of the layers that happened to be sampled.

Over all 31 layers it is roughly a wash — 7 come out ahead of nocsim, geomean 1.092×, spanning 0.71× to 3.32×.

Bigger lines win outright across the whole 16–64 B range, on every layer, with or without prefetching.

Prefetching costs cycles at 32 and 64 bytes, by up to 90%. It pays only at 16-byte lines, and never enough to catch a 64-byte line with prefetching off.

L2 banking changes nothing — at most 2.1% on a single point, and in the wrong direction. The L2 port is never the constraint here.

The layout

Where each digit sits

The kernel position is pos = kh × KW + kw, nine values for a 3×3 kernel. It is split at min(8, KH×KW) and the four digits nest, outermost first, as [pos_hi][cout_blk][cin_blk][pos_lo].

Nine values do not fit in three bits, and that is the deliberate trade: position 8 aliases onto position 0's set and is told apart by a tag bit. A value reached one time in nine does not earn a fourth index bit.

pos_hi · 1b
cout_blk · 7b
cin_blk · 5b
pos_lo · 3b
tag · 11 bitsL1 set index · 5 bits

V8 at 64-byte lines: 3×3 kernel, 32 CIN blocks of 16, 128 COUT blocks of 4, a 16 KB 8-way L1 of 32 sets. The index is pos_lo whole plus the low 2 bits of cin_blk. A core owns a fixed slice of COUT, and cout_blk is 8 bits above the index, so a pinned digit cannot narrow the sets a core reaches.

The mapper is KhkwSplitMapper, a sibling of BlockPackMapper and SplitCinMapper rather than a flag on either. It takes no split-width argument: the radix comes from the kernel, so cin_lo_blocks stays at its sentinel and there is no config field that can disagree with the layer.

All layers

The winning configuration, over every layer of both networks

Everything else on this page is four layers. This is the single best point above — 64-byte lines, one L2 bank, no prefetch — run over all 31 valid layers, 12 of vgg16 and 19 of resnet19, five samples each, against a nocsim baseline regenerated for the same 31 layers on the same schedules.

The four layers of the sweep reproduce their rows above to the digit, on both the cache side and the nocsim side, so the other 27 sit on the same code path and the same config rather than a re-tuned one.

The L2 hit rate is 0.00% on all 31 layers, the maximum anywhere in the set being 0.00%. The capacity cliff the four-layer probe located is therefore not an artifact of those four: at 512 KB and 16-way, this L2 returns nothing for any layer either network has. The L1 carries the workload alone, between 92.26% and 99.97%.

Against nocsim, 7 of 31 layers come out ahead, geomean 1.092×. The spread is wide and it is structured: V10 reaches 3.32× while V9 sits at 0.71×.

What separates them is not the cache. It is how much slack the baseline has: nocsim's own cycles over its own compute floor, which ranges from 1.00× to 10.04× across the set. That ratio predicts the speedup almost exactly (r = 0.978). On 22 of the 31 layers nocsim is already sitting on its floor, within 5%, and 0 of those 22 can be beaten by anything — there are no cycles there to win back, whatever the memory system does. Of the 6 layers where nocsim runs more than 1.5× its floor, 5 fall to the cache.

The L1 hit rate is the tempting explanation and it is the weaker one (r = -0.876). R2 is the case that breaks it: a 99.87% L1, near the top of the set, and still 1.33× ahead, because its baseline had 1.38× of slack to give. Read the L1 column as what the layout achieved, and the floor column as what was available to achieve.

A consistency check the reader can audit: 3 groups of layers land on identical nocsim cycle counts — R1/R3, R8/R10, R15/R17. Those are shape-identical layers, the same case LAYER_SWAP.md recorded for V8 and V9, whose tensors and next-layer CIN match so the solver returns the same schedule. Their cache numbers match within each group too, while V8 and V9 differ because there the spikes differ rather than the shape.

Axis 1

Line size: bigger is better, everywhere

At no prefetch and one bank. Every step from 16 to 64 bytes cuts cycles and raises the L1 hit rate, on all four layers. Nothing in this range trades off against anything.

The reason is spatial: cin_block is line_bytes / 4, so a 64-byte line packs 16 CIN of one COUT quad. A burst walks COUT, and consecutive tiles walk CIN, so the wider line is consumed rather than carried. Padding stays flat across the three sizes — 14.98% on V8 at both 32 and 64 bytes — which says the extra bytes are used, not wasted.

Why it costs anything at all

The next_burst prefetcher issues one request per line of the next burst. With the L1 already at 97.0%, 94% of those requests find the line resident and drop — but the L1 port slot is spent before the array is probed, by design: at l1_ii 1 every prefetch takes a cycle the demand stream could have used.

So it roughly doubles L1 port traffic to buy a few thousand timely fills out of 2.6 million issued. On V8 at 64 bytes, stall_l1_port goes from 0 to 2.44 million core-cycles. Raising the distance recovers part of it by spreading the requests out, never all of it.

A prefetcher that helped at 64 bytes would have to check residency before spending the port. That is a different policy, not a different distance.

Axis 3

L2 banking is inert

Cycles relative to one bank, meaned over four layers and five samples. Nothing moves. The largest single-point effect anywhere in the 720 comparisons is +2.1%, and the sign is wrong: more banks, marginally more cycles.

The cause is traffic, not wiring. Banking splits the L2's ports so that concurrent probes to different sets need not queue, and at the sweep's best point the L2's port-contention stall is exactly zero — there is no queue to split. The L2 sees 77,824 demand probes where the L1 sees 2,597,632, one for every 33.

Banking is a knob for a workload whose L2 is hot. Under this layout the L1 keeps the L2 cold, so the two facts are the same fact.

Hit rates

The L1 absorbs almost everything; the L2 falls off a cliff

The L1 numbers are in the tables above. The L2 number needs its own explanation, because it reads 0.00% at nearly every point of the sweep and a flat zero is not a result a reader can act on.

Walking l2_size_bytes from the sweep's 512 KB to 16 MB at the best point shows it is a pure capacity cliff, and shows exactly where the edge is: the L2 hit rate jumps from 0 to 52.63% the moment the cache can hold the layer's whole weight set — 4 MB for V8 and V9, 2 MB for R16. Not before, not gradually.

That is LRU meeting a cyclic sweep. The layer is walked start to end, over and over; at any size under the working set, every line is evicted before it is used again. Above it, every line is fetched exactly once and the 2.11 accesses per line collapse to 1.

R9 is the exception and it is the good kind. Its 0.28 MiB already fits in 512 KB, so its 0.00% means every line reaches the L2 once and never comes back — the L1 is holding it. A 16 MB L2 changes nothing for R9.

The practical reading: for V8, V9 and R16 the swept 512 KB L2 is on the wrong side of the edge and is buying nothing. Crossing it is worth 15% of V8's remaining cycles and 13% of R16's.

The same point — 64-byte lines, one bank, no prefetch — run under all three layouts in the tree, on all four layers and all five samples. Without this the speedups above could not be attributed.

khkw_split wins on every layer, on cycles, on L1 hit rate, and on DRAM traffic. The margin over block_pack runs from 2.2× to 3.0×, and over split_cin from 1.5× to 3.3×. Provenance

What ran, and how to run it again

Held fixed across the sweep, read back off a result row rather than retyped: 16 KB 8-way L1, 512 KB 16-way L2 with 32 MSHRs, cout_block 4, 1-byte weights, l1_latency 0, l2_latency 2, l2_miss_latency 24, LRU, non-inclusive, 16 cores.

Swept: line size {16, 32, 64} B (as cin_block = line_bytes / 4), l2_banks {1, 2, 4, 8}, prefetch_distance {0, 1, 2, 4}. Distance 0 carries prefetch_policy: none, since validate() refuses next_burst at distance 0 rather than silently running as none.

Line size is not an axis inside one sweep invocation: BroadcastSweep gives one mapper to the whole grid, so the 48 points run as three grids of 16, each over its own pass of the stream. That is 60 invocations rather than 960 process launches.
